# DDD分析 Skill

## 功能概述

本skill用于根据用户的需求描述进行深度的DDD（领域驱动设计）分析和建模。**支持增量更新**，避免重复覆盖已有文档。

## 使用时机

当用户的需求描述中包含以下关键词时，立即使用本skill：
- DDD分析
- DDD建模
- 领域建模
- 识别聚合根
- 分析业务概念
- 设计限界上下文
- 更新DDD设计

## 前置依赖规范

本Skill执行过程中，必须严格遵循：
- [01-architecture-constraints.md](../../rules/01-architecture-constraints.md) - DDD架构约束
- [09-ddd-document-format.md](../../rules/09-ddd-document-format.md) - DDD设计文档格式规范（**此规范定义了文档的必须格式和章节**）

## 分析步骤

### 第一步：检查已有文档 📂

在开始分析前，首先检查：
1. `docs/ddd-models/` 目录是否存在
2. 是否已有设计文档
3. 如有，阅读已有文档，了解当前设计状态

### 第二步：需求理解与差异分析 🔍

1. **理解新需求**
   - 提取关键业务概念（名词、动词、业务规则）
   - **特别关注用户需要的功能点和接口**
2. **对比已有设计**
   - 如果已有文档，识别：
     - ✅ **新增内容**：之前没有的概念
     - 🔄 **修改内容**：之前有但需要变更的
     - ❌ **删除内容**：不再需要的

### 第三步：识别限界上下文

根据业务概念的内聚性，划分限界上下文：
- 识别语义边界
- 确定上下文名称
- 说明每个上下文的职责

### 第四步：设计领域模型

对每个限界上下文，详细设计：
- 聚合根（Aggregate Root）
- 实体（Entity）
- 值对象（Value Object）
- 领域服务（Domain Service）
- 仓储接口（Repository）
- 领域事件（Domain Event）

### 第五步：梳理关系

明确：
- 聚合之间的关系
- 限界上下文之间的映射关系
- 上下文集成方式

### 第六步：识别功能点和接口 ⭐

**这是关键步骤，为 ddd-developer 提供输入：**

1. **识别待实现功能点**
   - 从需求中提取用户需要的功能
   - 每个功能点是一个垂直切片（从Interface到Domain）
   - 明确每个功能点涉及的层级
   - 按优先级排序（P0 > P1 > P2）

2. **识别待实现接口**
   - 对每个功能点，设计对应的RESTful接口
   - 明确HTTP方法、路径、请求/响应DTO
   - 明确ApplicationService方法名
   - 明确涉及的聚合

### 第七步：生成/更新文档

严格按照 `09-ddd-document-format.md` 规范输出结构化的DDD设计文档。

### 第八步：需求验证与补充 🔄

**这是关键的验证步骤！** 必须执行，确保文档完整覆盖需求：

**循环限制：最多3次** ⚠️

---

#### 单次验证流程：

1. **系统性比对**
   - 将生成的文档内容与原始需求描述逐行、逐项比对
   - 使用检查清单确认需求完整性

2. **识别遗漏**
   - 检查所有需求点是否都在文档中有体现
   - 识别隐含需求（如用户信息、时间戳、原因记录等）

3. **补充与更新**
   - 如果发现遗漏，更新文档补充内容
   - 标记新增/更新的内容

4. **判断是否继续循环**
   - **如果发现遗漏**：继续下一次循环
   - **如果确认完整**：退出循环
   - **如果达到3次限制**：停止，向用户说明并让用户判断

---

**需求验证检查清单：**
| 检查项 | 说明 |
|-------|------|
| ✅ 所有明确提到的实体/值对象 | 检查原始需求中的名词 |
| ✅ 所有业务规则 | 检查约束条件、计算规则 |
| ✅ 所有状态/流程 | 检查状态流转、触发条件 |
| ✅ 隐含需求 | 用户信息、时间戳、原因记录等 |
| ✅ 扩展性设计 | 是否便于后续扩展（如物流、退款、发票） |

---

**超过限制时的输出示例：**
> ⚠️ 已进行3次验证循环，仍有潜在改进空间
> 
> 当前已补充的内容：
> - [x] UserId
> - [x] CancelReason
> - [x] ShipmentInfo
> 
> 请判断是否还需要继续补充，还是认为当前已足够？

## 增量更新策略 ⚠️

### 文档存在时的处理

1. **备份现有文档**（可选）
   - 如果用户要求，先备份当前版本到 `docs/ddd-models/archive/`

2. **变更标记**
   - 在文档中使用以下标记说明变更：
     - `[NEW]` - 新增内容
     - `[UPDATED]` - 修改内容
     - `[DEPRECATED]` - 废弃内容

3. **版本记录**
   - 在文档末尾添加变更日志

## 文档格式规范

**所有文档严格遵循 [09-ddd-document-format.md](../../rules/09-ddd-document-format.md) 规范：**

- 总览文档必须包含第5章节「待实现功能清单」
- 限界上下文文档必须包含第4章节「待实现接口清单」
- 章节顺序严格按照规范
- 各部分格式符合规范要求

## 输出规范

### 目录结构

```
docs/ddd-models/
├── archive/                    # 历史版本备份
│   └── {版本日期}/
│       ├── {项目名称}-DDD-Overview.md
│       └── {限界上下文}-Context.md
├── {项目名称}-DDD-Overview.md  # 总览文档（最新）
└── {限界上下文}-Context.md     # 每个限界上下文一个文件（最新）
```

### 文件命名规范

- 总览文档：`{项目名称}-DDD-Overview.md`（项目名称默认用"ai-demo"）
- 限界上下文文档：`{限界上下文名称}-Context.md`（使用驼峰命名）
- 备份目录：`archive/{YYYYMMDD}/`

### 关键输出要求

1. **总览文档必须包含第5章节「待实现功能清单」**
2. **限界上下文文档必须包含第4章节「待实现接口清单」**
3. **所有章节顺序严格按照09-ddd-document-format.md规范**

## 执行流程

当用户触发本skill时，按以下流程执行：

1. **检查现有文档**
   - 列出 `docs/ddd-models/` 下所有文件
   - 如存在，阅读并分析

2. **分析新需求**
   - 仔细阅读用户需求
   - 提取关键业务概念
   - **特别关注功能点和接口需求**

3. **对比差异**
   - 识别：新增、修改、删除的内容

4. **识别功能点和接口**
   - 生成「待实现功能清单」（总览文档第5章）
   - 生成「待实现接口清单」（各限界上下文文档第4章）

5. **生成/更新文档**
   - 严格遵循 [09-ddd-document-format.md](../../rules/09-ddd-document-format.md) 规范
   - 如是首次，直接生成
   - 如已有，按增量更新策略更新文档
   - 添加变更日志
   - 如需备份，先备份到 `archive/`

6. **需求验证与补充（循环进行，最多3次）🔄**
   - **系统性比对**：将文档内容与原始需求逐行、逐项比对
   - **识别遗漏**：使用检查清单检查所有需求点和隐含需求
   - **补充更新**：如果发现遗漏，更新文档并增加版本号
   - **再次验证**：重复比对过程
   - **循环控制**：最多3次，超过则向用户说明并请求判断
   - **完成条件**：确认所有内容与需求完全相符

7. **输出总结**
   - 列出所有变更的文档
   - 说明哪些是新增、修改、删除
   - 说明验证过程（是否经过补充循环）
   - 提供后续建议（如配合 ddd-developer skill 实现）

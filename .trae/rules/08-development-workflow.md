# 开发流程规范（7阶段TDD）

&gt; **AI Agent必须严格遵守此流程！**

## 📋 前置步骤：项目初始化 ⚙️（可选）
**目标**：快速搭建项目基础结构，确保可编译、可运行

**适用场景**：
- 项目代码不存在（src/ 目录为空或不存在）
- pom.xml 不存在
- 主启动类不存在

**执行步骤**：
1. **检查项目状态**
   - 检查是否存在 pom.xml
   - 检查 src/ 目录结构
   - 检查 .gitignore 是否存在

2. **创建项目基础配置**
   - 创建 pom.xml（使用 03-spring-boot-guide.md 中的完整配置模板）
   - 创建 application.yml（H2数据库配置、MyBatis-Plus配置）
   - 创建 .gitignore（标准Java项目配置）
   - 创建主启动类（@SpringBootApplication）

3. **创建架构约束测试**
   - 创建 `arch-unit-constraints-test.groovy`（根据 01-architecture-constraints.md 的内容）
   - 测试必须覆盖：
     - Domain层禁止导入MapStruct、MyBatis-Plus、Spring Web
     - Interface层只能依赖Application层
     - Application层只能依赖Domain层
     - Infrastructure层只能依赖Domain层
     - 各层对象转换必须通过MapStruct
   - **重要**：此时此测试应该失败（因为还没有代码），但必须确保测试代码本身可以编译通过

4. **验证项目初始化成功**
   - 运行 `mvn compile` 确保编译成功
   - 运行 `mvn test-compile` 确保测试代码编译成功
   - 确保没有错误

5. **提交变更**
   - 提交信息格式：`INIT: [项目初始化描述]`
   - Git commit 包含所有初始化文件

**检查清单**：
- [ ] pom.xml 已创建，包含所有必需依赖
- [ ] application.yml 已创建
- [ ] 主启动类已创建
- [ ] arch-unit-constraints-test.groovy 已创建
- [ ] mvn compile 成功
- [ ] mvn test-compile 成功
- [ ] Git commit 已提交

## 📋 7阶段核心工作流程

### 阶段1：任务分析与规划 📊
**目标**：理解需求，拆分子任务

**执行步骤**：
1. 仔细阅读任务描述
2. 识别涉及的DDD分层
3. 列出需要创建/修改的领域对象
4. 将大任务拆分为独立子任务（每个子任务不超过3个文件）
5. 生成作战计划文档到 `task/{任务名称}/{任务名称}TaskPlan.md`

**输出**：作战计划文档

---

### 阶段2：编写失败的测试（红灯）🔴
**目标**：先写测试，定义期望行为

**执行步骤**：
1. 根据任务创建Spock测试文件
2. 测试必须覆盖：正常路径、失败路径、边界条件
3. **不要创建任何实现代码**
4. 提交信息格式：`FAILING TEST: [子任务描述]`
5. Git commit 仅包含测试文件

**检查清单**：
- [ ] 测试文件已创建，命名正确（`*Spec.groovy`）
- [ ] 测试方法以`should`开头
- [ ] 包含given-when-then结构
- [ ] 包含负面测试（null、异常、业务规则拒绝）
- [ ] 没有创建实现代码
- [ ] Git commit已提交

---

### 阶段3：最小实现（绿灯）🟢
**目标**：刚好让测试通过的最少代码

**执行步骤**：
1. 根据测试，编写最小实现代码
2. **严格遵守**DDD分层依赖规则
3. 不要添加额外功能（不要"顺便"做）
4. **必须运行**`mvn clean verify`，**如果测试失败，必须解决问题**，禁止跳过
5. **解决问题策略**：
   - 仔细阅读错误日志，理解失败原因
   - 检查是否违反架构约束
   - 检查代码逻辑是否正确
   - 必要时回退到上一步，重新检查
6. 只有所有测试通过后，才能提交
7. 提交信息格式：`IMPLEMENT: [子任务描述]`

**检查清单**：
- [ ] 代码放在正确的包内
- [ ] 没有违反架构约束
- [ ] **所有测试通过（mvn test）**
- [ ] 没有添加额外功能
- [ ] 如有测试失败已解决
- [ ] Git commit已提交

---

### 阶段4：重构与审查（清洁）🧹
**目标**：在不改变行为的前提下优化代码

**执行步骤**：
1. 在测试保护下进行重构
2. 消除重复代码
3. 改善命名，使其体现业务意图
4. 确保代码在正确的包内
5. **必须运行**`mvn clean verify`，**如果测试失败，必须解决问题**，禁止跳过
6. **解决问题策略**：
   - 仔细阅读错误日志，理解失败原因
   - 检查重构是否改变了行为
   - 必要时撤销部分重构
7. 只有所有测试通过后，才能提交
8. 提交信息格式：`REFACTOR: [重构说明]`

**检查清单**：
- [ ] 没有改变业务行为
- [ ] 代码更清晰易读
- [ ] 没有重复代码
- [ ] **所有测试通过**
- [ ] 如有测试失败已解决
- [ ] Git commit已提交

---

### 阶段5：端到端验证 ✅
**目标**：确保功能在所有层次正确集成，编译、运行、接口都正常

**执行步骤**：
1. **编译验证**
   - 运行 `mvn clean compile` 确保编译成功，没有错误
   - 运行 `mvn clean test-compile` 确保测试代码编译成功

2. **测试验证**
   - 如果涉及跨层协作，编写或执行集成测试（`*IT.groovy`）
   - 运行 `mvn clean test` 确保所有单元测试通过
   - 运行 `mvn clean verify` 确保所有测试通过

3. **运行验证**
   - 启动应用，确保 `mvn spring-boot:run` 可以正常启动
   - 检查启动日志，没有错误和异常
   - 确认应用在正确的端口监听（默认8080）

4. **接口验证**
   - 对于Web接口，使用curl或浏览器验证真实响应
   - 验证所有接口端点返回正确的状态码
   - 验证请求响应数据格式正确

5. **数据库验证**
   - 确保MyBatis-Plus操作实际生效（不要只mock）
   - 验证数据正确写入H2数据库
   - 可以通过H2 Console访问验证（http://localhost:8080/h2-console）

**检查清单**：
- [ ] **mvn clean compile 成功**
- [ ] **mvn clean test-compile 成功**
- [ ] **mvn clean test 成功**
- [ ] **mvn clean verify 成功**
- [ ] **mvn spring-boot:run 应用可以正常启动，并且没有错误或者异常日志**
- [ ] 接口验证成功
- [ ] 数据库操作正确
- [ ] 没有破坏现有功能

---

### 阶段6：文档同步与宣布完成 📝
**目标**：更新文档，宣布任务完成

**执行步骤**：
1. 检查本次改动是否需要更新文档
2. 列出所有完成的子任务
3. 列出通过的测试数量
4. 说明任何已知限制
5. 宣布任务完成

**检查清单**：
- [ ] 相关文档已更新
- [ ] 任务清单已标记完成
- [ ] 已知限制已说明
- [ ] 任务已宣布完成

---

### 阶段7：持续改进与回顾 🔄
**目标**：检查实现质量，完善规范和Skill，实现流程进化

**执行步骤**：
1. **规范与Skill检查**
   - 阅读当前所有的规范和skill内容
   - 检查是否存在冗余、边界不清晰、描述不明确的情况
   - 如果发现问题，完善对应的rule或skill

2. **业务与架构检查**
   - 根据DDD文档和已有代码，判断业务功能是否实现正确
   - 检查架构是否符合规范

3. **代码质量检查**
   - 根据所有代码开发规范约束，判断当前实现是否存在问题
   - 检查是否有违反架构约束、编码规范的情况

4. **测试覆盖检查**
   - 判断所有的测试是否缺失
   - 检查是否缺少单元测试、集成测试、边界测试

5. **规范与Skill进化**
   - 如果发现问题，在对应的rule或skill增加约束来完善
   - 实现rule和skill的持续进化

6. **Git操作与PR**
   - 提交所有代码
   - 新建branch
   - 使用GitHub MCP进行推送代码
   - 新建PR

**检查清单**：
- [ ] 规范和Skill已检查，无冗余、边界清晰
- [ ] 业务功能实现正确，架构符合规范
- [ ] 代码质量符合所有规范约束
- [ ] 测试覆盖完整，无缺失
- [ ] 如有必要，已完善rule和skill
- [ ] 代码已提交，branch已创建并推送
- [ ] PR已创建

**相关Skill**：
- 可使用 `code-review-and-improve` Skill来自动化完成此阶段

## 🚨 红线规则（绝对不能违反）

| # | 规则 | 后果 |
|---|------|------|
| 1 | 绝对不能在阶段2前写实现代码 | PR被拒绝，任务重置 |
| 2 | 提交的代码必须通过ArchUnit测试 | 根据失败日志修正分层违规 |
| 3 | 测试必须包含负面场景 | 反馈循环强制重写测试 |
| 4 | 一个commit不能同时包含测试和实现 | 任务被打回，必须拆分 |
| 5 | 不能自创架构规则 | 视为架构漂移，任务暂停 |
| 6 | **阶段3、4中，mvn test失败时必须解决问题，禁止跳过** | 暂停任务，直到问题解决 |
| 7 | **阶段5必须确保：编译成功、启动成功、测试通过、接口正常** | 任务不算完成，需继续验证 |

## 核心思想

### 基本原则

1. **业务优先**：技术服务于业务，先深入理解业务领域规则，再进行技术设计
2. **统一语言**：开发、产品、测试、业务专家等所有角色使用一致的术语沟通
3. **分而治之**：将复杂的业务领域拆分为多个边界清晰的子领域，每个子领域独立设计
4. **演进式设计**：DDD 是一个迭代过程，需要持续完善和调整模型

### 两个关键阶段

- **战略设计**：划分业务边界，解决"业务边界怎么划"的问题
- **战术设计**：领域模型的代码落地，解决"代码怎么写"的问题

## 战略设计约束

### 通用语言（Ubiquitous Language）

**核心要求**：
- 产品文档、代码、接口、数据库表、测试用例都使用同一套术语
- 避免"翻译成本"：产品叫 A，开发写 B，数据库存 C

**示例**：
| 场景 | 反例 | 正例 |
|---|---|---|
| 术语使用 | 产品：订单履约；开发：`OrderSendService`；数据库：`t_delivery` | 产品、开发、数据库统一使用"订单履约"术语 |

### 子领域划分

将领域分解为三类子领域：

| 子领域类型 | 定义 | 资源投入优先级 |
|---|---|---|
| **核心域** | 业务成功的关键差异化因素，需要最精细的建模 | ⭐⭐⭐ 最高 |
| **支撑域** | 支持核心域但不具有差异化优势的领域 | ⭐⭐ 中等 |
| **通用域** | 多个业务都会用到的通用功能（如认证、日志） | ⭐ 最低，可考虑开源组件 |

### 限界上下文划分原则

1. **按业务能力划分**，而非按技术组件划分
2. **同一上下文内保持模型一致性**
3. **不同上下文通过上下文映射交互**
4. **限界上下文是微服务拆分的重要依据**

### 上下文映射模式

明确限界上下文之间的关系和交互方式：

| 映射模式 | 适用场景 | 特点 |
|---|---|---|
| **合作关系 (Partnership)** | 两个上下文团队紧密协作 | 共同维护模型，同步变更 |
| **共享内核 (Shared Kernel)** | 多个团队共享核心模型 | 共享部分领域模型，需同步变更 |
| **防腐层 (ACL)** | 与遗留系统/外部系统集成 | 隔离外部模型污染，转换为本上下文模型 |
| **开放主机服务 (OHS)** | 提供标准化 API 给多个下游 | 定义公开协议，下游自行适配 |
| **遵奉者 (Conformist)** | 下游完全依赖上游模型 | 无自主权，完全遵循上游模型 |
| **发布语言 (Published Language)** | 多个上下文之间通信 | 定义公共语言（API、数据格式） |

## 战术设计约束

### 实体 vs 值对象

| 特征 | 实体（Entity） | 值对象（Value Object） |
|---|---|---|
| **标识** | 有唯一标识 | 无标识，通过属性值判断相等 |
| **可变性** | 可变（生命周期内状态会变） | 不可变（创建后不能修改） |
| **相等性** | 标识相等性 | 属性值相等性 |
| **生命周期** | 有完整生命周期，需要追踪 | 无生命周期，可随时创建/丢弃 |
| **示例** | 订单（Order）、用户（User） | 金额（Money）、地址（Address） |

### 领域服务设计原则

1. **不属于任何实体/值对象**的业务逻辑
2. **涉及多个聚合的协调操作**
3. **无状态**，不持有业务状态
4. **命名应该是动作**，如 `TransferService`、`BookingFactory`

### 领域模型组件要求

#### 聚合根（Aggregate Root）
- 唯一标识的设计
- 生命周期管理
- 对外暴露的行为方法
- 不变性约束

#### 实体（Entity）
- 具有唯一标识，生命周期内标识不变
- 通过标识判断相等性
- 包含业务行为

#### 值对象（Value Object）
- 无唯一标识，仅通过属性值判断相等性
- 不可变（创建后不能修改，只能整体替换）
- 包含业务逻辑（如金额计算）

#### 领域服务（Domain Service）
- 不属于任何实体/值对象的业务逻辑
- 涉及多个聚合的协调操作
- 无状态

#### 仓储接口（Repository）
- 定义在领域层，实现在基础设施层
- 提供聚合的增删改查操作
- 不暴露技术细节

#### 领域事件（Domain Event）
- 表示领域中发生的重要事情
- 包含发生时间、相关数据
- 用于跨聚合/上下文的解耦通信

## 聚合设计铁律

来自《实现领域驱动设计》的 4 条铁律，**必须严格遵守**：

| 序号 | 铁律 | 说明 |
|---|---|---|
| 1 | **聚合根是聚合的唯一外部入口** | 外部绝对不能直接访问聚合内的实体或值对象 |
| 2 | **一个事务只能修改一个聚合根** | 跨聚合的修改必须通过最终一致性实现 |
| 3 | **聚合之间只能通过聚合根的 ID 引用** | 绝对不能直接引用聚合根对象 |
| 4 | **聚合根删除时，聚合内的所有对象必须一起删除** | 聚合是数据一致性的边界 |

### 聚合设计最佳实践

1. **聚合应该尽量小**：只包含真正需要保持强一致性的对象
2. **优先使用值对象**：值对象更简单、更安全、更容易测试
3. **用最终一致性处理跨聚合操作**：使用领域事件、消息队列
4. **通过 ID 引用其他聚合**：避免对象图过大

## 验收标准

### DDD 设计文档验收标准

- [ ] 包含完整的子领域划分
- [ ] 包含清晰的限界上下文定义
- [ ] 包含上下文映射关系
- [ ] 每个限界上下文包含聚合设计
- [ ] **每个限界上下文必须有对应的详细设计文档**（文件名格式：`{ContextName}-Context.md`）
- [ ] **限界上下文数量与详细设计文档数量必须一致**，不得遗漏任何一个
- [ ] 包含详细的领域模型（实体、值对象、领域服务、仓储、领域事件）
- [ ] 包含待实现功能清单（优先级排序）
- [ ] 包含待实现接口清单（HTTP 方法、路径、DTO）
- [ ] 所有术语符合统一语言要求
- [ ] 文档结构符合 `09-ddd-document-format.md` 规范

### 步骤12：需求验证与补充的强制性检查

在步骤12的验证过程中，**必须执行以下检查清单**：

1. **限界上下文与文档一致性检查**
   - [ ] 列出总览文档中提到的所有限界上下文
   - [ ] 检查是否每个限界上下文都有对应的详细设计文档
   - [ ] 验证限界上下文数量与文档数量一致
   - [ ] 如有缺失，必须补充完整后才能结束

2. **需求完整性检查**（已存在）
   - [ ] 所有明确提到的实体/值对象
   - [ ] 所有业务规则
   - [ ] 所有状态/流程
   - [ ] 隐含需求（用户信息、时间戳、原因记录等）
   - [ ] 扩展性设计（是否便于后续扩展）
